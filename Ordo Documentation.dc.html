1 · Overview

Ordo coordinates production work across machines, robots, vehicles and people. A production process is modelled as a pipeline: a directed graph of stages that can branch into parallel work and merge back. Software agents run each stage against live plant data: they plan, assign resources, adjust parameters and decide when a stage is complete. Every decision is logged with its reason and a confidence score.

People stay in control through three mechanisms. The autonomy level sets how much agents may do without asking. Approval gates stop a pipeline at points where a person must sign off. Validation packages require a process engineer to prove that a stage, process change or new pipeline works, with measured checks and attached evidence, before quality and management sign it into use.

RolePrimary use of Ordo
OperatorExecutes manual stages, records manual checks, raises holds
Process engineerBuilds pipelines, prepares validation packages, attaches proof
Quality engineerReviews checks and evidence, signs quality gates, requests changes
Plant managerFinal approval, sets autonomy level per line, handles escalations
AdministratorUsers, roles, sites, connectors, policies

2 · Core concepts

2.1 Pipeline and stage

A pipeline is a template plus a run. The template defines stages, their order, parallel branches, rework loops, the agent and resource for each stage, its success criteria, timeout and escalation role. A run is one execution of a template against an order or batch, identified as R-2417.

Stages in the same column run in parallel and are numbered with a letter suffix (02a, 02b). When two adjacent columns have the same number of parallel stages, each lane continues on its own; otherwise lanes merge into the next stage. A rework loop sends units from a later stage back to an earlier one.

2.4 Autonomy levels

Autonomy is set per line and can be lowered for a single stage. A validated stage can be promoted one level (for example L3 → L4) as the outcome of an approved validation package.

2.5 Gates and validation packages

A gate is a stop point inside a run. It can be released directly (Approve), held (Hold), or released through a validation package. A validation package is a formal record that proves a stage, process change, pilot, machine qualification or proof of concept meets stated acceptance criteria. It contains scope, checks, evidence, a signature chain and an audit trail. Section 6 describes the workflow.

3 · Screens

The console has seven screens, reached from the left navigation. Counts beside Validation and Approvals show items waiting on the current user.

3.1 Pipelines

The header shows the run, template selector, view switch (Flow, Graph, Ledger), Step run and Edit in builder. Step run advances the run one column; it stops at a gate that is awaiting approval or held and opens that gate instead. Approving a gate completes its stage. Below it, the autonomy control and six run metrics: progress, rolled yield, live throughput, run ETA, agent decisions and pending gates. The decision stream at the bottom lists the latest agent decisions with reason and confidence.

  • Flow: each stage is a numbered node. Edge color follows the downstream state: dark for completed, gold for active, dashed grey for queued.
  • Graph: the same graph with compact cards on a dot grid, for dense pipelines.
  • Ledger: one row per stage with the full outcome text, timing, yield and throughput, for reading and printing.

3.2 Stage detail panel

Full details on a node block opens the side panel, which holds everything known about the stage:

  • Status, agent and assigned resource
  • Outcome summary
  • Human approval gate with Approve, Hold and Validate with evidence
  • Timing, yield, throughput, progress
  • Quality metrics against targets
  • Inputs and outputs (lot genealogy)
  • Alerts and exceptions
  • Decision log: time, action, reason, agent, confidence

3.3 Validation

The left list shows all validation packages with status, what each is waiting on, and progress through the six steps. Filters: All, Needs me, In review, Closed. New from current pipeline creates a package from the active gate or running stage.

The workspace has a step tracker (Draft → Agent pre-check → Submitted → QE review → Approval → Released), a readiness bar for the owner, and five numbered sections: Scope & acceptance, Validation checks, Proof & evidence, Sign-off, and Audit trail. Acting as switches the signed-in role for demonstration.

3.4 Templates

The library of 15 pipeline templates, filterable by category. Each card lists its stage chain (parallel stages joined with “+”), stage and gate counts, and offers Run pipeline or Customize (opens the builder). Appendix A lists all templates.

3.5 Run history

Runs from the last seven days with start, duration, a per-stage outcome strip, yield, agent decisions, human interventions and outcome. Filter by outcome; click a row to open its pipeline.

3.6 Floor & fleet

Assets groups every machine, robot, vehicle and station by zone with status, current job, utilization, OEE and owning agent. Agents shows each agent's scope, autonomy level, current task, decisions today, escalations and average confidence.

3.7 Approvals & exceptions

The operational inbox for quick decisions raised by agents during a run: quality gates, supplier substitutions, capacity calls and equipment exceptions. Each item shows the agent's evidence, the options it considered with the recommended one marked, and its confidence. Approve selected option, Reject & hold, or open the stage in its pipeline. Decisions that need formal proof go to Validation instead.

3.8 Pipeline builder

Edit a template's stages: add from the palette, reorder, remove. For the selected stage set the name, assigned resource, execution mode (Auto, Approve, Manual), success criteria, timeout and escalation role. Publish pipeline creates a new template version.

4 · System architecture

Ordo is organised in five layers. Shop-floor equipment (L1) connects through an on-premise edge gateway (L2) to a cloud data platform (L3). The orchestration core (L4) reads plant state, runs agents and pipelines, and writes decisions and signatures back to the data platform. The experience layer (L5) serves the console, notifications and public API. Enterprise systems connect at L3/L4 through versioned connectors.

4.2 Key flows

  1. Sense. Machines publish signals through the edge gateway to the event bus. The plant state model updates in near real time.
  2. Decide. An agent proposes an action with reason and confidence. The policy guard allows, escalates or blocks it.
  3. Act. Allowed actions flow down as job orders, setpoints and AGV missions. The pipeline engine advances the stage when its success criteria are met.
  4. Validate & sign. At a gate, the validation service assembles checks and evidence. People sign in sequence and the gate releases.

6 · Validation & sign-off workflow

6.1 Package types

TypeUsed to proveTypical outcome on approval
Stage validationA stage on a specific run meets its criteriaGate released; stage may move up an autonomy level
Process changeA changed parameter, recipe or profile is safeChange becomes the line default
Pilot validationA new recipe or method works across pilot batchesAdded to approved list
Proof of conceptA new pipeline or part replacement is viableNew pipeline published at L2
Operational qualificationA new or repaired asset performs like existing onesAsset joins the agent pool

6.2 Steps

  1. Draft. The process engineer defines objective, acceptance criteria, sample plan and trial window. Checks are seeded from the stage's success criteria.
  2. Agent pre-check. The owning agent fills in every automated check from run data, attaches generated evidence (logs, SPC charts, reports), and writes an assessment with key figures and confidence.
  3. Submit. The engineer records manual checks (Pass / Fail), attaches required evidence and signs as Performed by.
  4. QE review. The quality engineer signs as Reviewed by, or requests changes / rejects with a mandatory comment.
  5. Approval. The plant manager signs as Approved by.
  6. Released. The outcome is applied (gate released, autonomy promoted, change made default) and recorded in the ledger.

6.3 Rules

  • Sign & submit is enabled only when the pre-check has run, every check is recorded, no check has failed and all required evidence is attached.
  • Only the role at the current step may sign. Each signature states its meaning and requires the reviewer to confirm they reviewed the checks and evidence.
  • Request changes and Reject require a comment. A returned package goes back to Draft for its owner; all later signatures are cleared on resubmit.
  • Re-running the pre-check after changes refreshes automated results and the assessment.
  • Files are hashed on upload. A changed file is a new version; earlier versions stay in the record.
  • Every action (create, attach, remove, check, sign, return, release) writes an audit entry.

7 · Agent decision model

Every agent action follows the same path, so it can be explained and replayed.

  1. Observe. The agent reads plant state, recent telemetry and model predictions for its scope.
  2. Propose. It forms an action (for example “Split batch across CNC-04 and CNC-05”), a plain-language reason referencing the data, and a confidence between 0 and 1.
  3. Check policy. The policy guard compares the action with the autonomy level, stage mode, guardrails (limits on setpoints, cost, quantity, safety) and confidence threshold. Result: allow, escalate to a role, or block.
  4. Execute or escalate. Allowed actions are dispatched. Escalated actions appear in Approvals with the alternatives the agent considered.
  5. Record. Action, reason, confidence, policy result and outcome are written to the decision log and audit ledger.

9 · Security & compliance

  • Identity and roles. SSO through the corporate identity provider. Role-based access per site and line; signing rights are bound to roles.
  • Electronic signatures. Each signature records signer, role, meaning, time and comment, and requires re-authentication. Designed to support regulated environments such as 21 CFR Part 11 and EU GMP Annex 11; qualification remains the customer's responsibility.
  • Records. Audit ledger is append-only and hash-chained. Evidence files are content-hashed and versioned. Retention is configurable per site.
  • Network. OT network is segmented; edge gateways connect outbound only over mutual TLS. Safety PLCs are read-only to Ordo.
  • Safety. Agents never bypass machine safety systems. If the cloud link drops, the edge gateway completes the current safe step and holds.
